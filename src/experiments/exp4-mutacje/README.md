PB4 — Мутации (manual)
4a — Добавление элемента (add)
Цель

Исследовать поведение приложения после добавления нового элемента и влияние выбранной стратегии синхронизации на количество HTTP-запросов и согласованность интерфейса.

Сценарий

Пользователь добавляет новый элемент в список:

вариант 1: после мутации выполняется повторный запрос (refetch)
вариант 2: состояние обновляется локально (setState)
Метрики
количество HTTP-запросов
корректность данных в UI
способ синхронизации
предсказуемость поведения
сложность реализации
Наблюдения
Вариант: refetch (POST → GET)
выполняется 2 запроса:
POST + GET
новый элемент всегда корректно отображается в UI
состояние интерфейса полностью синхронизировано с сервером
поведение предсказуемо
реализация простая
Вариант: setState (POST → без GET)
выполняется 1 запрос:
POST
UI обновляется локально без повторного запроса
отсутствует дополнительная сетевая нагрузка
корректность зависит от реализации
выше ответственность разработчика
Выводы
ручной подход позволяет уменьшить количество HTTP-запросов
вариант с setState более эффективен по сети
вариант с refetch обеспечивает более надёжную синхронизацию
синхронизация данных не происходит автоматически и требует явной логики
4b — Удаление элемента (delete)
Цель

Проанализировать поведение приложения после удаления элемента и оценить корректность синхронизации данных.

Сценарий

Пользователь удаляет элемент из списка:

вариант 1: выполняется refetch
вариант 2: используется локальное обновление (setState)
Метрики
количество HTTP-запросов
корректность данных в UI
способ синхронизации
предсказуемость поведения
сложность реализации
Наблюдения
Вариант: refetch (DELETE → GET)
выполняется 2 запроса:
DELETE + GET
элемент корректно исчезает из UI
отсутствуют устаревшие (“фантомные”) данные
синхронизация полная
поведение предсказуемо
Вариант: setState (DELETE → без GET)
выполняется 1 запрос:
DELETE
элемент удаляется локально из UI
отсутствует дополнительный GET
возможен риск рассинхронизации при ошибках реализации
требуется ручной контроль состояния
Выводы
ручной подход позволяет сократить количество запросов
setState устраняет необходимость refetch
refetch обеспечивает более надёжную синхронизацию
корректность UI полностью зависит от логики разработчика
Итог PB4 (manual)
Ключевые наблюдения
после мутации синхронизация не происходит автоматически
разработчик должен явно выбрать стратегию обновления данных:
refetch (надёжно, но дороже по сети)
setState (эффективно, но требует контроля)
Итоговые выводы
ручной подход даёт контроль над количеством запросов
возможно уменьшение сетевой нагрузки
увеличивается сложность реализации
возрастает риск ошибок синхронизации
