Связь с гипотезой: все шесть PB рассматривают разные аспекты одной гипотезы: выбор способа управления server-state влияет на количество и предсказуемость HTTP-запросов, а React Query обеспечивает более системное и согласованное управление этим поведением по сравнению с ручной реализацией. Каждый PB проверяет эту гипотезу в отдельном измерении: получение → асинхронная синхронизация → актуальность → мутации → параметры → координация.
Общий ожидаемый вывод исследования: задача не в доказательстве превосходства React Query в каждом отдельном сценарии. Manual может обеспечивать такое же корректное поведение, особенно после добавления Context, cache, TTL, защиты от race и других механизмов. Но по мере усложнения server-state эти механизмы приходится проектировать и согласовывать вручную, тогда как React Query предоставляет единую модель queryKey + cache + freshness + query lifecycle + invalidation. Поэтому итоговая проверка гипотезы должна опираться одновременно на сетевые измерения (число и повторяемость запросов) и на архитектурные наблюдения (где находится ответственность за обеспечение такого поведения).# Обоснование структуры исследования PB1–PB6

## 1. Общая логика исследования

Исследование сравнивает два подхода к управлению `server-state` в React-приложении:

- **Manual** — управление средствами React и стандартного JavaScript/browser API;
- **React Query** — управление `server-state` средствами TanStack React Query.

Цель исследования состоит не в доказательстве того, что определённые задачи невозможно реализовать вручную.

Практически все рассматриваемые сценарии могут быть корректно реализованы обоими способами.

Предмет сравнения:

> **как выбор подхода к управлению server-state влияет на сетевое поведение приложения, объём и расположение управляющей логики, необходимость ручной координации состояния и предсказуемость поведения при усложнении сценария.**

Поэтому исследовательские вопросы разделены не по используемым API и не по возможностям библиотеки, а по **различным типам ответственности, возникающим при работе с server-state**.

Общая последовательность:

```text
PB1 — POBIERANIE
Как получить один server-state?

        ↓

PB2 — SYNCHRONIZACJA
Как согласовать его с асинхронным
жизненным циклом запросов?

        ↓

PB3 — AKTUALNOŚĆ
Когда уже полученный server-state
следует считать актуальным?

        ↓

PB4 — MUTACJE
Как поддержать согласованность
после изменения данных на сервере?

        ↓

PB5 — PARAMETRY
Как различать server-state,
зависящий от параметров запроса?

        ↓

PB6 — KOORDYNACJA
Как один server-state используется
и согласуется между несколькими
потребителями?
```

Таким образом, каждый следующий вопрос добавляет новое измерение проблемы управления `server-state`.

---

# 2. PB1 — Pobieranie

## Основной вопрос

> Как способ управления server-state влияет на количество и предсказуемость запросов при получении одного и того же ресурса?

PB1 является исходной точкой исследования.

Здесь ещё не рассматриваются:

- ошибки;
- race condition;
- freshness;
- мутации;
- параметризованный cache;
- распространение изменений между представлениями.

Исследуется фундаментальная операция:

```text
component → request → server-state
```

---

## Основные аспекты

PB1 последовательно рассматривает:

### Базовое получение

Что происходит при первоначальном mount компонента.

Здесь проявляется в том числе влияние React `StrictMode` на ручную реализацию и отличие поведения query-механизма.

### Несколько компонентов

Что происходит, если несколько **независимых потребителей** запрашивают один ресурс.

Этот сценарий позволяет наблюдать масштабирование количества запросов.

### Повторное появление потребителя / SPA-навигация

Что происходит, если компонент исчезает и затем снова появляется.

Здесь впервые возникает возможность повторного использования ранее полученного состояния.

---

## Главная ответственность PB1

```text
ПОЛУЧЕНИЕ
+
ПОВТОРНОЕ ПОЛУЧЕНИЕ
+
ДЕДУПЛИКАЦИЯ ЗАПРОСОВ
```

---

## Тонкая граница PB1 ↔ PB6

PB1 с несколькими компонентами может внешне напоминать PB6.

Однако в PB1 компоненты рассматриваются как **независимые инициаторы получения данных**.

Вопрос:

> сколько запросов возникает, когда несколько компонентов самостоятельно требуют один ресурс?

PB6 начинает исследование уже после архитектурного решения проблемы:

> как организовать один общий server-state для нескольких потребителей?

Поэтому:

```text
PB1
несколько consumers
→ независимое получение
→ сетевой эффект

PB6
один shared state
→ несколько consumers
→ архитектура координации
```

PB6 не должен повторно доказывать дедупликацию запросов PB1.

---

# 3. PB2 — Synchronizacja

## Основной вопрос

> Как способ управления server-state влияет на согласованность состояния приложения с жизненным циклом асинхронных сетевых операций?

После PB1 данные уже умеем получать.

Но асинхронность создаёт новую ответственность: результат запроса должен быть правильно согласован с текущим состоянием приложения.

PB2 разделён на три аспекта:

```text
                 SYNCHRONIZACJA
                       │
        ┌──────────────┼──────────────┐
        │              │              │
       RACE        BACKGROUND       ERRORS
        │              │              │
   актуальность    фоновый        результат
    результата     lifecycle        запроса
```

---

## PB2 / Race condition

### Вопрос

> Какой результат имеет право изменить состояние, если несколько запросов выполняются одновременно?

Исследуется:

```text
request A
request B
request C
    ↓
ответы приходят
в другом порядке
```

Manual должен самостоятельно определить актуальность результата.

React Query связывает состояние с соответствующим `queryKey`.

### Ответственность

```text
ЗАПРОС ↔ АКТУАЛЬНЫЙ РЕЗУЛЬТАТ
```

---

## PB2 / Background

### Вопрос

> Как организуется фоновое обновление и как состояние приложения согласуется с выполняющимся background request?

Финальная структура:

```text
Base
 ↓
Visibility
 ↓
Visibility + delayed
```

`Base` создаёт контрольную точку.

`Visibility` добавляет фоновое обновление.

`Delayed` делает промежуточное состояние запроса наблюдаемым.

### Ответственность

```text
ACTIVITY APPLICATION
        ↕
BACKGROUND REQUEST
        ↕
       UI
```

---

## Почему из Background удалены Predictability / competing requests

Если одновременно запускаются два запроса и исследуется:

- порядок их завершения;
- stale response;
- `requestId`;
- защита от применения старого результата,

то предмет исследования становится идентичным Race condition.

Поэтому такие сценарии не являются самостоятельным Background-экспериментом.

---

## PB2 / Errors & Retry

### Вопрос

> Как server-state и UI согласуются с успехом, ошибкой и повторным выполнением запроса?

Исследуются переходы:

```text
request
 ↓
loading
 ↓
success / error
 ↓
retry
 ↓
loading
 ↓
result
```

Manual самостоятельно поддерживает взаимосвязанные состояния.

React Query предоставляет состояние жизненного цикла query.

### Ответственность

```text
REQUEST LIFECYCLE
       ↕
data / error / loading
```

---

# 4. PB3 — Aktualność

## Основной вопрос

> Когда ранее полученный server-state следует считать достаточно актуальным для повторного использования, а когда требуется новый запрос?

PB3 вводит **время** как самостоятельное измерение server-state.

Ключевые понятия:

```text
fresh
  ↕
stale
```

Manual реализует соответствующую политику через собственный TTL/cache.

React Query использует `staleTime` и cache.

---

## Логика подэкспериментов

### 3a — Baseline

Нет осознанной политики freshness.

Создаётся контрольная точка.

### 3b — Page return

Проверяется политика актуальности при возвращении к представлению внутри приложения.

### 3c — Tab return

Та же проблема рассматривается при возвращении пользователя к браузерной вкладке.

---

## Почему 3b и 3c не являются дублями

Политика freshness одна, но **триггеры проверки состояния различаются**.

```text
3b
SPA/navigation/remount
        ↓
проверка freshness

3c
возвращение browser tab
        ↓
проверка freshness
```

Важный принцип:

> `TTL` и `staleTime` определяют fresh/stale, но сами по себе не являются запросом. Для повторного получения данных необходим соответствующий триггер.

---

## Тонкая граница PB2 Background ↔ PB3

Оба эксперимента могут использовать возвращение пользователя во вкладку.

Но исследуемая переменная различается.

### PB2

```text
background update уже инициирован
↓
как организуется его lifecycle?
```

### PB3

```text
пользователь вернулся
↓
fresh или stale?
↓
нужен ли request?
```

Короткая формула:

> **PB2 — как происходит update.  
> PB3 — нужен ли update с точки зрения freshness.**

---

# 5. PB4 — Mutacje

## Основной вопрос

> Как после изменения серверных данных поддерживается согласованность client-side server-state и какой сетевой эффект имеют различные стратегии синхронизации?

До PB4 server-state преимущественно читается.

PB4 впервые вводит изменение состояния сервера:

```text
client
  ↓
POST / DELETE
  ↓
server changed
  ↓
client state должен
соответствовать результату
```

---

## Две стратегии

После рефакторинга Manual и React Query сравниваются симметрично.

### Повторная серверная синхронизация

```text
Manual → refetch
Query  → invalidateQueries
```

Сетевая последовательность:

```text
GET
 ↓
MUTATION
 ↓
GET
```

### Локальное применение результата

```text
Manual → setState
Query  → setQueryData
```

Сетевая последовательность:

```text
GET
 ↓
MUTATION
```

---

## Подэксперименты

### Add

Проверяется добавляющая мутация.

### Delete

Проверяется удаляющая мутация.

Они представляют два направления изменения коллекции и позволяют проверить, сохраняется ли закономерность для разных типов мутации.

---

## Почему отдельный 4c больше не нужен

Ранее отдельный сценарий `synchronization` должен был исследовать необходимость согласования после мутации.

После рефакторинга именно это уже является предметом Add и Delete.

Поэтому 4c логически превращается в **аналитическое сопоставление результатов**, а не в третий искусственный эксперимент.

---

## Главная ответственность PB4

```text
SERVER MUTATION
       ↓
CLIENT SERVER-STATE
       ↓
RESTORE CONSISTENCY
```

---

# 6. PB5 — Parametry

## Основной вопрос

> Как параметр запроса влияет на идентичность server-state и возможность повторного использования ранее полученных данных?

PB5 вводит новое понятие:

```text
resource + parameter = конкретный server-state
```

Например:

```text
todos(all)
todos(active)
todos(completed)
```

являются связанными, но различимыми состояниями данных.

---

## Основная последовательность

### Изменение параметра

```text
all → active → completed
```

Проверяется связь между параметром и получаемым состоянием.

### Возврат к параметру

```text
completed → all
```

Проверяется, существует ли ранее полученный `all` как идентифицированное состояние, которое можно повторно использовать.

Manual требует собственной структуры parameter-cache.

React Query представляет идентичность через:

```js
queryKey: ["pb5", "todos", filter];
```

---

## Почему старый fast-change не является самостоятельным PB5

Сценарий:

```text
all
 ↓ быстро
active
 ↓ быстро
completed
```

при незавершённых запросах создаёт прежде всего:

- конкурирующие запросы;
- изменение порядка ответов;
- stale response.

Это предмет PB2 / Race.

Поэтому скорость переключения параметров не должна становиться самостоятельной исследовательской переменной PB5.

---

## Тонкая граница PB5 ↔ PB2 Race

```text
Race
parameter change используется,
чтобы создать конкуренцию запросов

PB5
parameter является частью
идентичности server-state
```

---

## Тонкая граница PB5 ↔ PB3

PB3 спрашивает:

> достаточно ли свежи сохранённые данные?

PB5 спрашивает:

> какие сохранённые данные относятся именно к этому параметру?

То есть:

```text
PB3 → freshness
PB5 → identity
```

`staleTime`, если он используется в PB5 для сохранения cache, является контролируемым условием, а не предметом исследования.

---

# 7. PB6 — Koordynacja

## Основной вопрос

> Как один server-state используется и остаётся согласованным между несколькими компонентами и представлениями приложения?

PB6 переносит исследование с отдельного потребителя на архитектуру приложения.

Manual рассматривается не только как простой `useState/useEffect`, но и с использованием стандартных архитектурных механизмов React:

- lifting state;
- props;
- Context API.

Это принципиально важно.

PB6 не должен создавать искусственно слабую Manual-реализацию.

---

# 8. PB6a — Shared

## Вопрос

> Как несколько компонентов могут использовать один server-state?

Сравниваются:

```text
Manual Props
Manual Context
React Query
```

Manual может централизовать получение данных и передавать единое состояние потребителям.

React Query предоставляет общий query/cache.

### Ответственность

```text
ONE SERVER-STATE
       ↓
MULTIPLE CONSUMERS
```

---

## Граница Shared ↔ PB1

PB1:

> что произойдёт, если несколько компонентов независимо получают один ресурс?

PB6:

> как архитектурно организовать один общий источник данных для нескольких компонентов?

Следовательно:

```text
PB1 → duplication / requests
PB6 → sharing / architecture
```

---

# 9. PB6b — Views

Это наиболее тонкая внутренняя граница PB6.

## Вопрос

> Как разные представления могут использовать один источник server-state без создания независимых копий состояния?

Например:

```text
                 TODOS
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
        list     count    statistics
```

Здесь исследуется уже не просто доступ нескольких компонентов к одному массиву.

Исследуется принцип:

> **один source of truth → несколько производных представлений.**

---

## Граница Shared ↔ Views

### Shared

```text
одни данные
↓
несколько consumers
```

### Views

```text
одни данные
↓
разные derived representations
```

Если Views описать только как «ещё несколько компонентов получили данные», он действительно станет повторением Shared.

Поэтому самостоятельность Views существует именно благодаря **различию представлений одного source of truth**.

---

# 10. PB6c — Update

## Вопрос

> Как изменение общего server-state, инициированное одним компонентом, становится видимым другим его потребителям?

Структура:

```text
Component A
     ↓
   update
     ↓
shared server-state
     ↓
 ┌───┴────┐
 ↓        ↓
B         C
```

Предмет исследования — **распространение изменения между потребителями**.

---

## Тонкая граница PB6c ↔ PB4

Это критически важная граница.

PB4 спрашивает:

> каким способом после мутации обновить client-side server-state?

Например:

```text
refetch?
invalidateQueries?
setState?
setQueryData?
```

PB6 не должен повторно сравнивать эти стратегии.

В PB6c мутация используется только как **стимул изменения общего состояния**.

Исследуется следующий этап:

```text
state изменился
       ↓
как это изменение
становится доступно
остальным consumers?
```

Короткая формула:

> **PB4 — как обновить state после mutation.  
> PB6 — как уже изменившийся shared state распространяется между потребителями.**

# 12. Карта наиболее опасных пересечений

## PB1 ↔ PB6

Общее:

- несколько компонентов;
- один ресурс.

Различие:

```text
PB1 → независимые запросы и их количество
PB6 → общий источник состояния и его потребители
```

---

## PB2 Race ↔ PB5

Общее:

- изменение параметров;
- несколько запросов.

Различие:

```text
Race → порядок async responses
PB5 → identity по parameter
```

---

## PB2 Background ↔ PB3

Общее:

- возвращение пользователя;
- возможность refetch.

Различие:

```text
Background → lifecycle выполняющегося update
PB3 → решение fresh/stale
```

---

## PB4 ↔ PB6 Update

Общее:

- изменение данных;
- обновление UI.

Различие:

```text
PB4 → каким способом синхронизировать state после mutation
PB6 → как изменение общего state распространяется consumers
```

---

Общее:

- один state;


# 13. Принцип выделения подэксперимента

Не каждое технически отличающееся поведение должно становиться отдельным экспериментом.

Самостоятельный подэксперимент оправдан тогда, когда он вводит **новую исследуемую переменную или отдельный аспект ответственности**.

Недостаточно основания:

> «код немного отличается».

Необходимо основание:

> «изменяется исследуемое условие, позволяющее ответить на отдельную часть исследовательского вопроса».

Поэтому:

### Оправдано

```text
Background Base
→ добавляем background trigger
→ добавляем наблюдаемую длительность

PB4 Add
→ добавляющая mutation

PB4 Delete
→ удаляющая mutation

PB6 Shared
→ shared access

PB6 Views
→ derived representations

PB6 Update
→ propagation of change
```

### Не оправдано

Создавать новый эксперимент только потому, что:

- используется другой handler;
- изменён delay;
- добавлен `requestId`;
- существует ещё один способ написать тот же код;
- тот же исследовательский эффект можно показать другим UI.

Если новый сценарий фактически отвечает на вопрос другого PB, он должен быть перенесён или исключён.

---

# 14. Принцип симметрии Manual ↔ React Query

Сравнение должно быть функционально симметричным.

Нельзя делать вывод о подходах, если им поставлены разные задачи.

Например, некорректное сравнение:

```text
Manual → local setState
Query → invalidate + GET
```

потому что сравниваются две разные стратегии.

Корректная структура:

```text
Manual refetch ↔ Query invalidateQueries

Manual setState ↔ Query setQueryData
```

То же относится к UI.

Если в эксперименте намеренно скрываются данные во время задержки, одинаковое наблюдаемое условие должно применяться к обеим реализациям либо различие должно быть частью исследуемой переменной.

---

# 15. Принцип «Manual не должен быть искусственно слабым»

Цель исследования — не противопоставить React Query примитивному или намеренно ошибочному React-коду.

Manual может использовать стандартные средства платформы:

- `useState`;
- `useEffect`;
- `Context API`;
- custom hooks;
- `AbortController`;
- debounce;
- собственный cache;
- TTL;
- props/lifting state;
- защиту от stale responses.

Если стандартный React-механизм естественно решает проблему, его использование допустимо.

Тогда сравнивается:

> **какую инфраструктуру необходимо построить вручную и какую ответственность специализированная библиотека берёт на себя.**

Именно поэтому особенно важен PB6: Props и Context показывают, что Manual может быть архитектурно корректным и масштабируемым, но требует явной организации общего состояния.

---

# 16. Принцип интерпретации BUG/FIX

BUG-сценарий оправдан только тогда, когда он демонстрирует **характерный риск исследуемого способа управления состоянием**.

Он не должен искусственно создаваться в React Query только ради симметрии.

Например, в Errors ручное хранение нескольких взаимосвязанных состояний позволяет продемонстрировать:

```text
request завершён
но loading остался true
```

или:

```text
retry выполняется
но loading не восстановлен
```

Это показывает риск пропущенного ручного перехода.

Нет необходимости специально ломать Query, если соответствующий переход является частью его модели query.

Симметрия эксперимента означает **одинаковую задачу и условия**, а не обязательное наличие одинаковой ошибки в обеих реализациях.

---

# 17. Принцип интерпретации результатов

Нельзя автоматически делать вывод:

> React Query лучше, потому что кода меньше.

Количество кода является дополнительным наблюдением, но не единственным исследовательским результатом.

Основными критериями остаются:

- количество HTTP-запросов;
- повторяемость сетевого поведения;
- корректность server-state;
- необходимость ручной синхронизации;
- количество взаимосвязанных состояний;
- наличие или отсутствие дополнительной инфраструктуры;
- место, где хранится ответственность за поведение;
- устойчивость решения при усложнении сценария.

Также нельзя утверждать:

> Manual не способен решить проблему.

Корректная интерпретация чаще выглядит так:

> оба подхода позволяют получить корректный результат, однако различаются способом организации и распределением ответственности за управление server-state.

---

# 18. Финальная логика всей экспериментальной части

Вся экспериментальная часть может быть сведена к последовательному усложнению одной задачи:

```text
                 SERVER-STATE
                      │
                      ↓
        PB1 — как его ПОЛУЧИТЬ?
                      │
                      ↓
        PB2 — как согласовать его
              с ASYNC lifecycle?
                      │
                      ↓
        PB3 — как определить его
              АКТУАЛЬНОСТЬ?
                      │
                      ↓
        PB4 — что делать, когда
              server-state ИЗМЕНИЛСЯ?
                      │
                      ↓
        PB5 — как различать его
              по ПАРАМЕТРАМ?
                      │
                      ↓
        PB6 — как КООРДИНИРОВАТЬ
              его между consumers?
```

Эта последовательность является главным обоснованием разделения исследования на шесть вопросов.

Каждый PB вводит новую ответственность, которой не было в предыдущем вопросе.

При этом пересечения пользовательских действий допустимы.

Один и тот же триггер — например, возврат во вкладку, изменение фильтра или мутация — может появляться в нескольких экспериментах, **если исследуемая переменная различается**.

Поэтому границы определяются не внешним действием пользователя и не названием используемого API, а вопросом:

> **какая именно ответственность управления server-state исследуется в данном эксперименте?**

Именно этот принцип следует использовать как основной критерий при дальнейшем описании экспериментов и интерпретации их результатов в магистерской работе.

## Предварительные выводы исследования

### 1. Выбор способа управления server-state действительно влияет на количество HTTP-запросов

**Основание: количественные измерения Network.**

Наиболее непосредственно это показано в PB1: при нескольких независимых потребителях Manual создаёт отдельные запросы, тогда как React Query может дедуплицировать запросы к одному `queryKey`. При повторном появлении компонента количество запросов также зависит от наличия и настроек cache/freshness.

PB4 дополнительно показывает, что количество запросов определяется не только выбором Manual/Query, но и выбранной стратегией после мутации: `refetch/invalidateQueries` создаёт дополнительный GET, тогда как `setState/setQueryData` позволяет локально применить результат без него.

**Тип доказательства:** количество и последовательность `GET/POST/DELETE` в DevTools Network.

---

### 2. Нельзя сделать общий вывод, что React Query всегда выполняет меньше запросов

**Основание: результаты PB1, PB3 и PB4.**

Количество запросов зависит от конфигурации и выбранной стратегии. Например, `staleTime` может предотвратить повторный запрос, но stale-данные при соответствующем trigger могут вызвать refetch. После мутации `invalidateQueries` также может привести к дополнительному GET.

Следовательно, React Query не минимизирует сетевой трафик автоматически во всех ситуациях.

**Тип доказательства:** сравнительное количество и последовательность HTTP-запросов при разных конфигурациях.

---

### 3. Оба подхода позволяют получить корректное поведение server-state

**Основание: исправленные Manual-варианты экспериментов PB2–PB6.**

Race condition можно устранить ручной защитой от stale response; freshness — собственным cache и TTL; мутации — `setState` или повторным fetch; параметризованные состояния — собственным parameter-cache; совместное использование состояния — lifting state, Props и Context.

Следовательно, эксперименты не показывают невозможность ручного управления server-state.

**Тип доказательства:** наблюдаемое корректное состояние UI и Network после применения соответствующих Manual-механизмов.

---

### 4. При усложнении server-state ручная реализация требует накопления дополнительных механизмов

**Основание: архитектурное сопоставление PB2–PB6.**

В различных экспериментах Manual потребовались дополнительные механизмы: защита от stale response, обработка `visibilitychange`, явные состояния loading/error, собственный cache и TTL, parameter-cache, lifting state/Props/Context и логика синхронизации после мутаций.

React Query решает соответствующие задачи в рамках общей модели query/cache.

**Тип доказательства:** качественный анализ фактически реализованного кода и распределения ответственности.

Это **не количественная сетевая метрика**, поэтому данный вывод должен подаваться как архитектурный результат исследования.

---

### 5. Предсказуемость поведения зависит от того, сколько правил синхронизации разработчик должен поддерживать самостоятельно

**Основание: поведенческие результаты PB2, PB3 и PB5.**

Race показывает риск применения результата уже неактуального запроса. Errors показывает зависимость Manual от корректного управления связанными состояниями `data/error/loading`. PB3 требует вручную согласовать TTL с событиями, способными инициировать refetch. PB5 требует явно связать параметр с соответствующим состоянием/cache.

В React Query эти отношения выражаются через общую модель `queryKey`, query lifecycle, cache и freshness.

**Тип доказательства:** повторяемость ожидаемого результата при заданном сценарии, корректность выбранных данных и соответствие сетевого поведения заданным условиям.

Здесь «предсказуемость» является **наблюдаемым поведенческим критерием**, а не одной числовой метрикой.

---

### 6. Преимущество React Query становится заметнее с ростом числа обязанностей server-state

**Основание: совокупное сравнение PB1–PB6.**

В простом сценарии получения данных различие между подходами относительно невелико. Последовательное добавление асинхронной синхронизации, freshness, мутаций, параметров и нескольких потребителей требует от Manual всё большей собственной инфраструктуры.

При этом React Query использует одну связанную модель:

`queryKey → cache → freshness → lifecycle → mutation/invalidation → shared consumers`.

**Тип доказательства:** совокупный качественный анализ архитектуры всех шести PB, подкреплённый сетевыми и поведенческими результатами отдельных экспериментов.

---

## Итог относительно гипотезы

Результаты **в целом поддерживают гипотезу**, но требуют её аккуратной интерпретации.

**Влияние подхода на количество HTTP-запросов подтверждается непосредственно количественными измерениями Network.**

**Различия в предсказуемости подтверждаются наблюдаемым поведением экспериментальных сценариев:** наличием или отсутствием лишних запросов, stale responses, корректностью выбора состояния, условиями повторного запроса и согласованностью состояния.

**Более системная организация server-state в React Query обосновывается архитектурным анализом реализованных решений:** функции, которые в Manual постепенно требуют отдельных механизмов, в React Query объединены общей моделью управления query-state.

Таким образом, исследование не доказывает, что React Query всегда создаёт меньше запросов или что Manual не способен обеспечить корректное поведение. Оно показывает, что **по мере роста сложности server-state ручной подход требует всё большего количества явно реализуемых и согласуемых механизмов, тогда как React Query предоставляет эти механизмы в рамках единой модели управления состоянием и сетевым поведением.**
