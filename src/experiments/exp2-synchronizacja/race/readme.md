# PB2 — Race condition

## 1. Исследовательский аспект

Данная часть PB2 исследует поведение `server-state` в ситуации, когда несколько асинхронных запросов выполняются одновременно, а порядок получения ответов не совпадает с порядком их запуска.

Сравниваются два подхода:

- **Manual** — ручное управление `server-state` средствами React;
- **React Query** — управление `server-state` средствами TanStack React Query.

Основной исследовательский аспект:

> Как выбранный способ управления server-state влияет на согласованность данных при конкурирующих асинхронных запросах?

Эксперимент проверяет, может ли результат более раннего, но медленно завершившегося запроса изменить состояние приложения после того, как пользователь уже инициировал новый запрос для другого состояния.

---

# 2. Место Race condition в PB2

PB2 исследует поведение приложения в асинхронных ситуациях, требующих согласования состояния интерфейса с жизненным циклом запросов.

Внутри PB2 разделяются три аспекта:

- **Race condition** — конкуренция запросов и применение результатов, пришедших в непредсказуемом порядке;
- **Background synchronization** — фоновое обновление после возвращения пользователя к приложению;
- **Errors / Retry** — обработка ошибок и повторных запросов.

Race condition отвечает на отдельный вопрос:

> какой результат должен иметь право изменить актуальное состояние приложения, если несколько запросов были запущены последовательно, но завершились в другом порядке?

---

# 3. Методология эксперимента

Для Manual и React Query воспроизводится одинаковый пользовательский сценарий.

Пользователь быстро изменяет параметр:

```text
all → active → completed
```

Каждое изменение инициирует отдельный асинхронный запрос.

Запросы выполняются с различной задержкой, поэтому ответы могут поступить не в том порядке, в котором были инициированы.

Общая последовательность:

```text
изменение filter
      ↓
запрос A
      ↓
новое изменение filter
      ↓
запрос B
      ↓
ответы приходят независимо
      ↓
проверка итогового server-state
```

Критерием корректности является соответствие отображаемых данных **текущему значению параметра**, а не последнему физически завершившемуся запросу.

---

# 4. Контролируемые условия

Для обеих реализаций сохраняются одинаковые условия:

- одинаковые данные;
- одинаковый источник данных;
- одинаковые значения `filter`;
- одинаковая последовательность действий пользователя;
- одинаковая модель асинхронной задержки;
- возможность изменения порядка завершения запросов;
- одинаковый ожидаемый результат.

Различается способ управления связью между запросом и актуальным состоянием приложения.

---

# 5. Архитектура эксперимента

Эксперимент состоит из параллельного воспроизведения одного сценария.

```text
                 Race condition
                       │
            ┌──────────┴──────────┐
            │                     │
         Manual              React Query
            │                     │
     запросы запускаются     запросы связаны
     при смене filter        с queryKey
            │                     │
     ответы изменяют         результаты принадлежат
     общий state             соответствующим query
            │                     │
       наблюдение итогового состояния
```

В Manual дополнительно рассматривается исправленный вариант, поскольку именно ручная реализация позволяет непосредственно продемонстрировать как возникновение ошибки, так и добавление защиты от неё.

---

# 6. Сценарий — конкурирующие запросы

## Исследуемый аспект

Проверяется, что произойдёт, если:

1. пользователь выбирает одно значение `filter`;
2. запускается запрос;
3. до его завершения пользователь выбирает другое значение;
4. запускается следующий запрос;
5. ответы приходят в порядке, отличном от порядка запуска.

Потенциальная проблема:

```text
старый запрос
   │
   │ медленный
   ↓
старый ответ ──────────────┐
                           ↓
новый запрос → новый ответ → state
                           ↑
             старый ответ может
             перезаписать результат
```

---

# 7. Manual — базовая реализация

В Manual изменение `filter` инициирует новый асинхронный запрос.

Полученный результат записывается в общий React-state.

Если несколько запросов выполняются одновременно, каждый из них после завершения способен выполнить обновление состояния.

При отсутствии дополнительной проверки компонент не знает, относится ли полученный ответ к **текущему** значению `filter`.

Следовательно, корректность итогового состояния может зависеть от порядка завершения асинхронных операций.

---

# 8. Manual — защита от stale response

Для устранения проблемы Manual должен дополнительно хранить информацию о том, какой запрос является актуальным.

При запуске нового запроса идентификатор актуальной операции изменяется.

После получения ответа выполняется проверка:

```text
ответ относится
к последнему запросу?
      │
 ┌────┴────┐
 │         │
да        нет
 │         │
 ↓         ↓
apply     ignore
```

Таким образом, stale response не должен изменять актуальное состояние.

Корректность достигается дополнительной логикой, реализованной разработчиком.

---

# 9. React Query

В React Query параметр запроса является частью его идентичности:

```js
queryKey: ["todos", filter];
```

При изменении `filter` изменяется и `queryKey`.

Следовательно, результаты запросов для:

```text
["todos", "all"]
["todos", "active"]
["todos", "completed"]
```

относятся к различным состояниям query.

Отображаемые данные выбираются в соответствии с текущим `queryKey`, а завершение запроса для предыдущего значения параметра не должно превращать его результат в данные другого ключа.

Поэтому в компоненте не требуется реализовывать собственный механизм `latestRequestId` для данного сценария.

---

# 10. Процедура

Для обеих реализаций:

1. Открыть эксперимент.
2. Установить исходный `filter`.
3. Быстро изменить значения фильтра последовательно.
4. Запустить тем самым несколько асинхронных запросов.
5. Наблюдать порядок их завершения.
6. Зафиксировать текущее значение `filter`.
7. После завершения всех запросов проверить отображаемые данные.
8. Сравнить результат Manual без защиты, Manual с защитой и React Query.

---

# 11. Наблюдаемые параметры

Фиксируются:

- последовательность запуска запросов;
- последовательность получения ответов;
- текущее значение `filter`;
- данные, отображаемые после каждого ответа;
- соответствие итоговых данных текущему параметру;
- возникновение stale response;
- необходимость дополнительной защиты;
- объём логики, необходимой для связывания результата с актуальным состоянием.

---

# 12. Результаты

## Manual без защиты

Если более ранний запрос завершается позже нового, его результат может изменить общий `state`.

В результате отображаемые данные могут временно или окончательно не соответствовать текущему значению `filter`.

## Manual с защитой

После добавления проверки актуальности ответа устаревший результат игнорируется.

Итоговые данные соответствуют текущему состоянию приложения.

Таким образом, Manual позволяет решить проблему, но требует дополнительного механизма контроля.

## React Query

При включении параметра в `queryKey` результаты запросов связываются с соответствующими состояниями query.

Изменение порядка получения ответов не приводит к тому, что результат одного `queryKey` становится результатом другого.

Итоговые данные соответствуют текущему значению `filter`.

# 14. Итоговый вывод Race condition

Эксперимент показывает, что проблема race condition связана не с самим фактом выполнения нескольких HTTP-запросов, а с тем, **как их результаты связываются с актуальным состоянием приложения**.

Manual позволяет обеспечить корректное поведение, однако для этого разработчик должен явно определить, какой ответ остаётся актуальным, и предотвратить применение устаревшего результата.

React Query использует идентичность query, включающую параметр запроса, поэтому результаты разных параметров относятся к соответствующим `queryKey`.

Следовательно, различие состоит не в возможности решить race condition, а в распределении ответственности за согласование результата запроса с актуальным `server-state`.

---

# 15. Границы эксперимента

## Race и Background

Race исследует:

> какой результат должен быть применён при конкуренции нескольких запросов.

Background исследует:

> как организуется фоновое обновление и как ведёт себя UI во время уже инициированного обновления.

Поэтому сценарии с двойными background-trigger и `latestRequestId` не включаются в Background.

---

## Race и PB5 — Parametry

Оба эксперимента используют изменение параметров, однако предмет исследования различается.

В Race параметр используется как средство создания **конкурирующих асинхронных операций**.

Исследуется:

> влияние порядка завершения запросов на корректность результата.

В PB5 параметр является частью **идентичности server-state**.

Там исследуются:

- изменение параметра;
- последовательность параметров;
- повторное использование состояния для уже встречавшихся параметров;
- параметризованный cache.

Следовательно, совпадение пользовательского действия не означает совпадения исследовательского вопроса.

---

# 16. Роль Race condition в проверке общей гипотезы

Race condition показывает один из случаев, в котором выбор способа управления `server-state` влияет на предсказуемость поведения приложения при асинхронных запросах.

Manual способен обеспечить корректность, однако требует дополнительного механизма определения актуального результата.

React Query связывает данные с идентичностью query, благодаря чему часть этой координации входит в используемую модель управления `server-state`.

Результат используется как один из элементов проверки общей гипотезы о влиянии выбранного подхода на предсказуемость сетевого поведения приложения.
