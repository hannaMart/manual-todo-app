# PB6c — Update: распространение изменений между компонентами

## 1. Исследовательский вопрос

Как выбранный способ управления server-state влияет на распространение изменений серверных данных между несколькими компонентами React-приложения?

## 2. Цель эксперимента

Проверить, как изменение серверных данных одним компонентом становится доступным другим компонентам, использующим общий server-state.

Сравниваются три реализации:

- Manual — Props;
- Manual — Context API;
- React Query — общий queryKey и cache.

PB6c исследует координацию компонентов после изменения данных, а не сравнение стратегий мутаций, рассмотренных ранее в PB4.

## 3. Условия эксперимента

Во всех трёх реализациях используются одинаковые исходные данные, компоненты и серверные операции.

Источник данных: PB6_TODOS из fakeServer/db.js.

Серверные функции:

- fakeFetchPb6UpdateTodos() — получение задач (GET);
- fakeAddPb6Todo() — добавление задачи (POST);
- resetPb6Todos() — восстановление исходного состояния.

Задержка серверных операций — 800 мс.

Сценарий включает три компонента:

- Component A — добавляет новую задачу.
- Component B — отображает полный список задач.
- Component C — отображает общее количество задач и статистику.

Во всех реализациях используется одинаковая последовательность синхронизации:

POST → GET → обновление общего состояния → обновление представлений.

В React Query повторное получение данных инициируется через invalidateQueries.

Для определения количества API-запросов используются логи fakeAPI.

## 4. Реализация Manual — Props

Файл: update/update-props.jsx

Общий массив задач хранится в useState родительского компонента UpdateProps.

Component A получает через props функцию handleAdd.

После добавления задачи родитель выполняет повторный GET-запрос и сохраняет обновлённый массив в useState.

Компоненты B и C получают обновлённые данные через props.

Схема:

Component A → POST → GET → useState родителя → props → B и C.

Отдельная синхронизация дочерних компонентов не требуется.

## 5. Реализация Manual — Context API

Файл: update/update-context.jsx

Общий массив задач и функция handleAdd находятся в TodosProvider.

Component A получает функцию изменения через useContext.

После успешного POST-запроса Provider выполняет GET-запрос и обновляет общий useState.

Компоненты B и C получают обновлённые данные через useContext.

Схема:

Component A → POST → GET → useState провайдера → Context API → B и C.

Передача данных и функции изменения через props не требуется.

При этом загрузка, хранение и синхронизация server-state реализуются разработчиком вручную.

## 6. Реализация React Query

Файл: update.jsx

Все компоненты работают с одним QueryClient и используют общий queryKey:

```jsx
["pb6-update-todos"];
```

Component A выполняет серверную операцию через useMutation.

После успешного POST-запроса вызывается:

```jsx
await queryClient.invalidateQueries({
  queryKey,
  exact: true,
});
```

React Query инициирует повторное получение данных и обновляет общую запись кэша.

Компоненты B и C используют useQuery с одинаковым queryKey и получают обновлённые данные из общего кэша.

Схема:

Component A → POST → invalidateQueries → GET → общий cache → B и C.

Для распространения изменений не требуется создавать пользовательский useState, передавать данные через props или самостоятельно организовывать общий Context.

## 7. Результаты проверки

Во всех трёх реализациях проверен одинаковый сценарий: первоначальная загрузка четырёх задач и добавление одной новой задачи.

### До добавления

| Показатель   | Значение |
| ------------ | -------: |
| Всего задач  |        4 |
| Выполнено    |        2 |
| Не выполнено |        2 |
| API-запросы  |    1 GET |

### После добавления

| Показатель                   |       Значение |
| ---------------------------- | -------------: |
| Всего задач                  |              5 |
| Выполнено                    |              2 |
| Не выполнено                 |              3 |
| API-запросы за весь сценарий | 2 GET + 1 POST |

Во всех трёх реализациях новая задача появилась в Component B, а Component C отобразил обновлённую статистику.

Количество API-запросов во всех вариантах совпало.

Отдельные запросы для обновления компонентов B и C не потребовались.

## 8. Сравнение реализаций

| Критерий                           | Manual — Props      | Manual — Context API  | React Query             |
| ---------------------------------- | ------------------- | --------------------- | ----------------------- |
| Общий источник состояния           | useState родителя   | useState провайдера   | QueryClient / cache     |
| Инициирование мутации              | Функция через props | Функция через Context | useMutation             |
| Синхронизация после POST           | Ручной GET          | Ручной GET            | invalidateQueries → GET |
| Распространение изменений          | props               | useContext            | Общий queryKey и cache  |
| Дополнительная синхронизация B и C | Не требуется        | Не требуется          | Не требуется            |
| API-запросы                        | 2 GET + 1 POST      | 2 GET + 1 POST        | 2 GET + 1 POST          |
| Итоговое количество задач          | 5                   | 5                     | 5                       |

## 9. Выводы

**1. Согласованность представлений.**

Все три реализации обеспечили согласованное обновление списка задач и статистики после успешной серверной операции и последующего GET-запроса.

**2. Ручное управление server-state.**

Использование общего useState позволяет избежать независимого хранения и отдельной синхронизации данных в каждом компоненте.

При использовании Props разработчик явно передаёт данные и функцию изменения через родительский компонент.

Context API предоставляет доступ к общему состоянию и функции изменения без передачи через props, но сама логика загрузки и синхронизации остаётся ручной.

**3. React Query.**

React Query обеспечивает распространение обновлённых данных через общий кэш.

После invalidateQueries библиотека выполняет повторное получение данных для активного запроса. Компоненты, использующие соответствующий queryKey, получают обновлённое состояние без необходимости самостоятельно организовывать его передачу.

**4. Количество API-запросов.**

Во всех реализациях зафиксировано одинаковое количество API-запросов: два GET и один POST.

В проверенном сценарии React Query не сократил количество обращений к API относительно ручных реализаций.

**5. Итог PB6c.**

Основное различие между подходами заключается в механизме организации общего состояния и распространения изменений между компонентами.

При корректной организации ручного управления server-state все три подхода обеспечивают одинаковый результат без дополнительных запросов для каждого компонента.

PB6c не устанавливает преимуществ какого-либо подхода по количеству запросов или согласованности конечного состояния.

## 10. Ограничения эксперимента

Исследование охватывает одну успешную мутацию и последующую синхронизацию общего server-state.

Не исследуются конкурентные мутации, ошибки серверных операций, независимый жизненный цикл компонентов и производительность повторных рендеров.

Полученные результаты относятся к реализованному сценарию и не распространяются автоматически на более сложные приложения.

## 11. Итог PB6

PB6 завершает экспериментальную часть исследования сравнением способов координации общего server-state между несколькими компонентами.

PB6a — совместный доступ к одинаковым серверным данным.

PB6b — формирование разных представлений общего server-state.

PB6c — распространение изменений между компонентами.

Во всех трёх частях оптимизированные ручные реализации и React Query обеспечили одинаковое количество API-запросов и согласованные конечные представления данных.

Основные различия проявились в архитектуре управления общим состоянием, способах доступа к нему и организации синхронизации.

Результаты PB6 подтверждают возможность достижения одинакового наблюдаемого поведения приложения разными механизмами управления server-state.
