# PB6b — Representations: разные представления общего server-state

## 1. Исследовательский вопрос

Как выбранный способ управления server-state влияет на формирование разных представлений одних и тех же серверных данных несколькими компонентами React-приложения?

В PB6b исследуется организация совместного использования одного набора серверных данных тремя компонентами, каждый из которых формирует собственное представление.

Сравниваются три реализации:

- Manual — Props;
- Manual — Context API;
- React Query — общий queryKey и cache.

Эксперимент направлен на выявление различий в организации доступа к общему server-state, получении производных данных и количестве API-запросов.

## 2. Цель эксперимента

Проверить, каким образом три компонента React-приложения могут формировать разные представления одного набора серверных данных без выполнения независимых API-запросов и создания отдельных источников server-state.

Установить:

1. Сколько API-запросов выполняется при одновременном монтировании трёх компонентов.
2. Используют ли компоненты один общий источник server-state.
3. Требуется ли создавать независимые копии серверных данных для формирования разных представлений.
4. Каким образом компоненты получают исходные данные и вычисляют производные значения.
5. Какие механизмы организации общего состояния используются в ручных реализациях и React Query.
6. Обеспечивается ли согласованность разных представлений одного набора серверных данных.

## 3. Место PB6b в структуре исследования

PB6a исследовал совместный доступ двух компонентов к одному server-state при одинаковом способе отображения данных.

PB6b расширяет этот сценарий: теперь три компонента используют один набор серверных данных, но отображают разные сведения о нём.

Таким образом, предметом PB6b является не только совместный доступ к данным, но и организация нескольких представлений общего состояния.

Изменение серверных данных и распространение результатов мутации между компонентами в PB6b не исследуются. Эти вопросы рассматриваются отдельно в PB6c.

## 4. Общие условия эксперимента

Во всех трёх реализациях используются одинаковые исходные данные, серверная операция и сценарий проверки.

### 4.1. Источник данных

Используется существующая коллекция TODOS из файла:

fakeServer/db.js

Исходное состояние:

| ID  | Title                   | Completed |
| --- | ----------------------- | --------- |
| 1   | Drink 2 litres of water | false     |
| 2   | Task 2                  | true      |
| 3   | Task 3                  | false     |
| 4   | Task 4                  | true      |

Общее количество задач — 4.

Выполненные задачи — 2.

Невыполненные задачи — 2.

### 4.2. Серверная функция

Для получения данных используется существующая функция:

fakeFetchPb6Todos()

Файл:

fakeServer/fakeAPI.js

Характеристики функции:

- имитирует асинхронное получение серверных данных;
- использует фиксированную задержку 800 мс;
- возвращает массив задач из коллекции TODOS;
- регистрирует начало и завершение каждого вызова в консоли;
- использует отдельный счётчик API-запросов PB6.

Функция возвращает объект следующей структуры:

```js
{
  requestId,
  todos: [
    { id: 1, title: "Drink 2 litres of water", completed: false },
    { id: 2, title: "Task 2", completed: true },
    { id: 3, title: "Task 3", completed: false },
    { id: 4, title: "Task 4", completed: true }
  ]
}
```

Во всех трёх реализациях используются эквивалентные серверные функции и одинаковые исходные данные.

### 4.3. Структура интерфейса

В каждом варианте используются три компонента.

Component A — Todo List:

Отображает полный список задач с их названиями и статусами выполнения.

Component B — Total:

Отображает общее количество задач.

Component C — Statistics:

Отображает количество выполненных и невыполненных задач.

Все три компонента используют один набор серверных данных.

Производные значения вычисляются из исходного массива todos.

Дополнительные API-запросы для получения количества задач или статистики не предусматриваются.

### 4.4. Ограничения сценария

Во время эксперимента:

- серверные данные не изменяются;
- параметры запроса не изменяются;
- компоненты используют один серверный ресурс;
- каждый компонент формирует своё представление из общего набора данных;
- отдельные серверные операции для получения статистики не используются.

Количество вызовов фиксируется по логам fakeAPI.

Поскольку используется имитация API без реального HTTP, в результатах фиксируются API-запросы, а не HTTP-запросы.

## 5. Реализация Manual — Props

Файл:

manual-todo-app/src/experiments/exp6-koordynacja/representations/representations-props.jsx

### 5.1. Организация состояния

Родительский компонент RepresentationsProps выполняет загрузку серверных данных с помощью useEffect.

Полученный массив todos сохраняется в локальном состоянии родителя с помощью useState.

Родитель также управляет состояниями загрузки и ошибки.

После успешного завершения запроса данные передаются трём дочерним компонентам через props.

Схема:

fakeAPI → RepresentationsProps (useState) → props → Component A / B / C

Каждый компонент получает один и тот же массив todos, но использует его по-разному.

```jsx
<TodoList todos={todos} />
<TodoTotal todos={todos} />
<TodoStats todos={todos} />
```

Дочерние компоненты не выполняют собственных API-запросов и не создают независимых состояний для хранения полученного массива.

### 5.2. Формирование представлений

Component A получает массив todos и отображает каждый элемент списка.

```jsx
{
  todos.map((todo) => (
    <li key={todo.id}>
      {todo.title} — {todo.completed ? "Done" : "Active"}
    </li>
  ));
}
```

Component B вычисляет общее количество задач:

```jsx
todos.length;
```

Component C вычисляет количество выполненных и невыполненных задач:

```jsx
const completed = todos.filter((todo) => todo.completed).length;

const active = todos.filter((todo) => !todo.completed).length;
```

Все производные значения вычисляются непосредственно из общего массива.

Дополнительное состояние для хранения количества задач или статистики не создаётся.

### 5.3. Результат проверки

При открытии страницы зафиксирован один API-запрос.

После завершения загрузки компоненты отображают:

- Component A — четыре задачи;
- Component B — Total todos: 4;
- Component C — Completed: 2, Active: 2.

Все представления соответствуют исходному состоянию серверных данных.

Дополнительные API-запросы для вычисления количества задач и статистики отсутствуют.

### 5.4. Вывод

Ручное управление server-state с помощью useState, useEffect и props позволяет организовать несколько представлений одного набора серверных данных без независимой загрузки и хранения данных в каждом компоненте.

Разработчик размещает общее состояние в родительском компоненте и передаёт исходный массив заинтересованным дочерним компонентам.

Каждый компонент самостоятельно формирует необходимые производные значения из полученных данных.

В проверенном сценарии один API-запрос обеспечивает работу всех трёх представлений.

## 6. Реализация Manual — Context API

Файл:

manual-todo-app/src/experiments/exp6-koordynacja/representations/representations-context.jsx

### 6.1. Организация состояния

В данной реализации используются TodosContext и TodosProvider.

TodosProvider выполняет загрузку серверных данных с помощью useEffect и сохраняет полученный массив в useState.

Также Provider хранит состояния загрузки и ошибки.

Общее состояние предоставляется дочерним компонентам через Context API.

Схема:

fakeAPI → TodosProvider (useState) → Context API → Component A / B / C

Каждый компонент получает исходный массив с помощью useContext:

```jsx
const { todos } = useContext(TodosContext);
```

Передача массива через props не требуется.

Компоненты не выполняют собственных API-запросов и не хранят независимые копии server-state.

### 6.2. Формирование представлений

Component A использует полученный из контекста массив для отображения полного списка задач.

Component B вычисляет общее количество:

```jsx
const { todos } = useContext(TodosContext);

const total = todos.length;
```

Component C вычисляет статистику:

```jsx
const { todos } = useContext(TodosContext);

const completed = todos.filter((todo) => todo.completed).length;

const active = todos.filter((todo) => !todo.completed).length;
```

Все производные значения вычисляются из одного массива, предоставленного TodosProvider.

Дополнительные независимые состояния для представлений не создаются.

### 6.3. Подключение Provider

Главный компонент RepresentationsContext самостоятельно подключает TodosProvider.

Содержимое страницы вынесено в RepresentationsContent, который находится внутри Provider и получает доступ к контексту.

```jsx
export default function RepresentationsContext() {
  return (
    <TodosProvider>
      <RepresentationsContent />
    </TodosProvider>
  );
}
```

Такая организация позволяет подключать RepresentationsContext непосредственно к существующей навигации приложения.

### 6.4. Результат проверки

При открытии страницы зафиксирован один API-запрос.

После завершения загрузки:

- Component A отображает четыре задачи;
- Component B отображает Total todos: 4;
- Component C отображает Completed: 2, Active: 2.

Все три компонента используют данные, предоставленные общим TodosProvider.

Дополнительные запросы для отдельных представлений отсутствуют.

### 6.5. Вывод

Context API позволяет организовать несколько представлений одного server-state без явной передачи исходного массива через props.

Компоненты самостоятельно получают данные из общего контекста и вычисляют необходимые производные значения.

При этом загрузка, хранение серверных данных и обработка состояний запроса остаются частью ручной реализации внутри TodosProvider.

В проверенном сценарии Context API обеспечивает одинаковое количество API-запросов и одинаковые результаты отображения по сравнению с Manual — Props.

Различие между реализациями заключается в способе предоставления исходных данных заинтересованным компонентам.

## 7. Реализация React Query

Файл:

query-todo-app/src/experiments/exp6-koordynacja/representations.jsx

### 7.1. Организация состояния

В реализации React Query все три компонента самостоятельно используют useQuery.

Для обращения к одному серверному ресурсу применяется одинаковый queryKey.

Общие настройки запроса:

```jsx
const queryOptions = {
  queryKey: ["pb6-todos"],
  queryFn: fakeFetchPb6Todos,
  staleTime: 60_000,
  refetchOnMount: false,
  refetchOnWindowFocus: false,
};
```

Главный компонент Representations также использует useQuery для управления состояниями загрузки и ошибки.

После завершения загрузки монтируются три дочерних компонента, каждый из которых выполняет собственный вызов useQuery с одинаковыми настройками.

Все компоненты работают с одним QueryClient.

React Query использует queryKey для идентификации общего server-state в кэше.

Схема:

Component A → useQuery → общий QueryClient / cache

Component B → useQuery → общий QueryClient / cache

Component C → useQuery → общий QueryClient / cache

Все три компонента обращаются к одной записи кэша, идентифицируемой queryKey ["pb6-todos"].

Родительский компонент не хранит серверный массив в собственном useState и не передаёт его дочерним компонентам через props.

### 7.2. Формирование представлений

Component A самостоятельно получает данные через useQuery и отображает полный список задач.

```jsx
const { data } = useQuery(queryOptions);
```

Component B также использует useQuery и вычисляет общее количество задач:

```jsx
const { data } = useQuery(queryOptions);

const total = data.todos.length;
```

Component C получает исходные данные из той же записи кэша и вычисляет количество выполненных и невыполненных задач.

```jsx
const { data } = useQuery(queryOptions);

const completed = data.todos.filter((todo) => todo.completed).length;

const active = data.todos.filter((todo) => !todo.completed).length;
```

Для каждого представления не создаётся отдельный queryKey.

Производные значения вычисляются непосредственно из общего массива задач.

### 7.3. Настройки эксперимента

Используются следующие параметры:

- staleTime: 60 000 мс;
- refetchOnMount: false;
- refetchOnWindowFocus: false.

Настройки ограничивают дополнительные запросы, не относящиеся непосредственно к проверке совместного использования данных.

В данной реализации родительский компонент сначала выполняет useQuery и обрабатывает состояние загрузки.

После получения данных монтируются три дочерних компонента, которые используют тот же queryKey и получают доступ к общей записи кэша.

Для независимой проверки количества API-запросов необходимо учитывать состояние QueryClient перед запуском сценария.

### 7.4. Результат проверки

При открытии страницы с исходным состоянием кэша зафиксирован один API-запрос.

После завершения загрузки:

- Component A отображает четыре задачи;
- Component B отображает Total todos: 4;
- Component C отображает Completed: 2, Active: 2.

Несмотря на то что родительский и три дочерних компонента используют useQuery, дополнительные API-запросы для отдельных представлений не выполняются.

Все компоненты получают доступ к общему результату запроса через одинаковый queryKey.

### 7.5. Вывод

React Query позволяет нескольким компонентам самостоятельно обращаться к одному server-state через useQuery и общий кэш.

Для получения разных представлений не требуется создавать отдельные запросы или независимые копии исходных серверных данных.

Каждый компонент получает доступ к общему набору данных и самостоятельно вычисляет необходимые производные значения.

В проверенном сценарии React Query обеспечил один API-запрос и согласованное отображение всех трёх представлений.

По количеству запросов и результатам отображения отличий от оптимизированных ручных реализаций не зафиксировано.

## 9. Общие выводы

### 9.1. Количество API-запросов

Все три реализации обеспечили формирование разных представлений одного набора серверных данных после выполнения одного API-запроса.

Ручное управление server-state позволяет избежать дублирования запросов при условии, что разработчик самостоятельно организует общий источник состояния.

React Query обеспечивает совместный доступ к серверным данным через общий кэш и одинаковый queryKey.

В проверенном сценарии различий в количестве API-запросов между тремя подходами не зафиксировано.

### 9.2. Организация общего server-state

В Manual — Props общий массив хранится в родительском компоненте и передаётся дочерним компонентам через props.

В Manual — Context API общий массив хранится в TodosProvider и предоставляется компонентам через Context API.

В React Query серверные данные находятся в общем кэше QueryClient, а каждый компонент получает к ним доступ через useQuery.

Во всех трёх вариантах разные представления формируются из одного общего набора данных без необходимости независимо загружать и хранить серверный массив в каждом компоненте.

### 9.3. Формирование производных данных

Количество задач, количество выполненных и количество невыполненных задач вычисляются непосредственно из исходного массива todos.

Для этих значений не создаются отдельные серверные ресурсы, независимые API-запросы или дополнительные состояния.

Следовательно, формирование разных представлений одного server-state не требует создания нескольких независимых источников данных.

Данный результат подтверждён во всех трёх реализациях.

### 9.4. Согласованность представлений

Во всех вариантах:

- полный список содержит четыре задачи;
- общее количество задач равно четырём;
- количество выполненных задач равно двум;
- количество невыполненных задач равно двум.

Значения статистики соответствуют исходному массиву, отображаемому в полном списке.

Таким образом, все три подхода обеспечили согласованность разных представлений при первоначальной загрузке неизменяемых серверных данных.

Этот результат не подтверждает автоматически согласованность после мутаций, повторных запросов или конкурентных изменений данных.

### 9.5. Различия между подходами

Manual — Props требует явной передачи массива от родительского компонента каждому дочернему компоненту.

Manual — Context API предоставляет общий массив через Provider и useContext, устраняя необходимость передавать исходные данные через props.

React Query предоставляет общий кэш и позволяет компонентам самостоятельно обращаться к одному серверному ресурсу через useQuery.

В проверенном сценарии различия между подходами проявляются в организации доступа к общему состоянию, а не в количестве API-запросов или значениях производных данных.

### 9.6. Ограничения эксперимента

PB6b рассматривает три компонента, формирующих разные представления одного неизменяемого набора серверных данных.

Эксперимент не исследует:

- изменение исходного массива после первоначальной загрузки;
- распространение результатов серверных мутаций;
- согласованность представлений в процессе асинхронного обновления;
- независимое монтирование и размонтирование компонентов;
- сложные деревья компонентов и передачу данных через промежуточные уровни;
- производительность вычисления производных значений;
- количество повторных рендеров;
- трудоёмкость сопровождения реализаций в крупных приложениях.

Полученные результаты не позволяют сделать общий вывод о превосходстве одного подхода над другим.

PB6b устанавливает, что все три исследуемые реализации способны обеспечить несколько согласованных представлений общего server-state без дополнительных API-запросов.

## 10. Переход к PB6c

Следующая часть исследования — PB6c (update).

В PB6a проверялся совместный доступ двух компонентов к одинаковым серверным данным.

В PB6b проверялось формирование разных представлений одного server-state тремя компонентами.

В PB6c будет исследоваться распространение результата изменения серверных данных между компонентами, использующими общий server-state.

Планируемый сценарий:

- Component A выполняет серверную операцию изменения задачи;
- Component B отображает список задач;
- Component C отображает количество задач и статистику.

После успешного завершения серверной операции компоненты B и C должны получить согласованное обновлённое состояние.

Сравниваются три реализации:

- Manual — Props;
- Manual — Context API;
- React Query — общий queryKey и cache.

PB6c не повторяет исследование стратегий мутаций из PB4.

Для всех трёх реализаций выбирается одна фиксированная схема синхронизации, согласованная по ожидаемому результату и серверным операциям.

Основной предмет исследования — механизм распространения результата изменения общего server-state между несколькими компонентами.
