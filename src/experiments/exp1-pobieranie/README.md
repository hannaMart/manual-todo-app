# PB1 — Повторные HTTP-запросы и сетевое поведение

## 1. Исследовательский вопрос

**Как выбор подхода к управлению server-state в React-приложении (ручной подход на основе `useEffect` / `useState` vs React Query) влияет на количество и предсказуемость повторных HTTP-запросов при типичных пользовательских сценариях?**

---

## 2. Цель

Цель PB1 — экспериментально определить, влияет ли способ управления server-state на количество HTTP-запросов и характер их повторного выполнения в типичных сценариях работы React-приложения.

Сравниваются два подхода:

- **Manual** — ручная загрузка и хранение server-state с использованием `useEffect`, `useState` и `fetch`;
- **React Query** — управление server-state с использованием `useQuery`, общего кэша и механизмов контроля актуальности данных.

PB1 рассматривает прежде всего **сетевое поведение приложения**. Предметом исследования является не визуальное представление данных и не удобство синтаксиса, а фактически выполняемые обращения к одному и тому же серверному ресурсу.

---

## 3. Место PB1 в общей структуре исследования

PB1 является исходной точкой всей экспериментальной части и исследует базовую проблему получения server-state и повторных запросов.

Общая последовательность исследовательских вопросов:

- **PB1** — базовое получение данных и повторные HTTP-запросы;
- **PB2** — ошибки, race conditions и асинхронное поведение;
- **PB3** — актуальность server-state во времени;
- **PB4** — мутации и последующая синхронизация;
- **PB5** — идентичность server-state при изменении параметров запроса;
- **PB6** — координация одного server-state между несколькими компонентами.

Таким образом, PB1 устанавливает базовые различия между двумя подходами, которые далее исследуются в более сложных условиях.

---

## 4. Обоснование исследовательского вопроса

Server-state в React-приложении получается из внешнего источника и обычно требует выполнения HTTP-запросов. Повторное получение уже запрошенных данных увеличивает сетевую активность приложения и может приводить к ненужному использованию ресурсов клиента и сервера.

При ручном подходе загрузка данных обычно связывается с жизненным циклом компонента: компонент монтируется, `useEffect` запускает `fetch`, результат сохраняется в `useState`. При повторном монтировании или наличии нескольких независимых компонентов эта логика может выполняться повторно.

React Query использует другую модель: серверные данные идентифицируются с помощью `queryKey` и могут совместно использоваться через кэш. Дополнительные механизмы библиотеки определяют, когда запрос должен быть выполнен повторно и когда существующие данные могут быть использованы без нового обращения к серверу.

Поэтому PB1 проверяет не теоретические возможности обоих подходов, а их фактическое сетевое поведение при одинаковых пользовательских сценариях.

---

## 5. Структура PB1

PB1 состоит из трёх завершённых экспериментов:

### Эксперимент 1 — базовая загрузка

Один компонент получает server-state при монтировании.

Исследуемый аспект:

**возникает ли различие между подходами уже при первоначальной загрузке данных?**

### Эксперимент 1a — масштабирование интерфейса

Десять компонентов одновременно запрашивают один и тот же серверный ресурс.

Исследуемый аспект:

**как изменяется количество запросов при увеличении числа компонентов, использующих одинаковые данные?**

### Эксперимент 1b — навигация и возврат

Пользователь выполняет последовательность:

`todos → about → todos`

Исследуемый аспект:

**приводит ли повторное монтирование представления к повторному запросу и каким образом на это влияет кэш и конфигурация React Query?**

Последовательность PB1:

**базовая загрузка → масштабирование → повторное использование данных после навигации.**

Использование одного endpoint и одного набора данных в обеих реализациях позволяет исключить различия в источнике данных и сосредоточить исследование на поведении клиентской части приложения.

Для PB1 важным является не содержание отдельных элементов `todos`, а факт выполнения HTTP-запроса к одному и тому же ресурсу и возможность его регистрации в Chrome DevTools.

## 7. Общие условия измерения

Для обеспечения сопоставимости результатов используются одинаковые условия измерения.

Chrome DevTools → **Network**:

- включён `Preserve log`;
- включён `Disable cache`;
- перед каждым независимым измерением журнал Network очищается;
- после подготовки измерения выполняется однократный `Reload`;
- учитываются запросы к исследуемому endpoint `/todos`.

`Disable cache` отключает HTTP-кэш браузера, но не отключает внутренний кэш React Query. Это принципиально важно, поскольку кэш React Query является частью исследуемого механизма управления server-state.

Manual и React Query используют:

- один источник данных;
- один endpoint;
- одинаковый пользовательский сценарий внутри соответствующего эксперимента;
- одинаковую структуру отображаемых данных;
- одинаковую последовательность действий пользователя.

Визуальное оформление интерфейса не является экспериментальной переменной.

## 8. Основная метрика

Основная количественная метрика PB1:

**количество HTTP-запросов к endpoint `/todos`, выполненных в рамках заданного сценария.**

Дополнительно анализируется:

- причина повторного запроса;
- связь запроса с монтированием компонента;
- наличие дедупликации;
- повторное использование ранее полученных данных;
- влияние кэша React Query;
- влияние `staleTime` и `gcTime`;
- предсказуемость момента повторного обращения к серверу.

Термин **«предсказуемость»** в рамках PB1 означает возможность однозначно связать выполнение или отсутствие повторного HTTP-запроса с определённым состоянием приложения и установленными правилами управления server-state.

# 9. Эксперимент 1 — базовая загрузка server-state

## 9.1. Исследуемый аспект

Проверяется поведение приложения при наиболее простом сценарии: один компонент монтируется и получает данные с сервера.

Эксперимент определяет исходную точку для дальнейшего сравнения.

---

## 9.2. Сценарий

1. Открывается приложение.
2. Монтируется компонент `Todos`.
3. Компоненту необходимы данные `/todos`.
4. Фиксируется количество HTTP-запросов.

Эксперимент выполняется в development-режиме React с включённым `React.StrictMode`.

---

## 9.3. Manual — useEffect + useState

В ручной реализации:

1. компонент монтируется;
2. `useEffect` запускает `fetch`;
3. выполняется запрос к `/todos`;
4. полученный результат сохраняется в `useState`;
5. компонент отображает данные.

Вся ответственность за момент получения данных находится внутри компонента.

---

## 9.4. React Query

В реализации React Query:

1. компонент монтируется;
2. вызывается `useQuery`;
3. запрос идентифицируется через `queryKey`;
4. React Query управляет выполнением запроса и полученным результатом;
5. данные становятся доступны компоненту.

---

## 9.5. Результаты

| Подход                      | HTTP-запросы |
| --------------------------- | -----------: |
| Manual — useEffect/useState |            2 |
| React Query                 |            1 |

---

## 9.6. Наблюдения

### Manual

В Chrome DevTools зарегистрировано **два запроса** к одному endpoint.

Причиной является `React.StrictMode` в development-режиме. Повторное выполнение жизненного цикла эффекта приводит к повторному запуску загрузки данных.

### React Query

При аналогичном сценарии зарегистрирован **один HTTP-запрос**.

React Query контролирует запрос через механизм управления query и не приводит в данном сценарии к двум независимым сетевым обращениям.

---

## 9.7. Визуальная фиксация

В магистерской работе результаты подтверждаются:

**Рис. 1.** Manual — два HTTP-запроса к `/todos`.

**Рис. 2.** React Query — один HTTP-запрос к `/todos`.

Скриншоты Chrome DevTools используются как дополнительная фиксация измерений, однако количественным результатом эксперимента остаётся число зарегистрированных запросов.

---

## 9.8. Вывод по эксперименту 1

Базовый эксперимент показывает, что различия между подходами могут проявляться уже при первоначальном получении server-state.

В ручной реализации выполнение запроса непосредственно связано с эффектом компонента, поэтому особенности его жизненного цикла могут приводить к повторному обращению к серверу.

React Query в исследованном сценарии выполняет один HTTP-запрос.

При этом результат данного эксперимента нельзя обобщать как утверждение, что ручная реализация всегда выполняет два запроса. Наблюдаемое различие связано с конкретным условием эксперимента — development-режимом и `React.StrictMode`.

Поэтому для проверки поведения независимо от `StrictMode` проводится эксперимент 1a.

---

# 10. Эксперимент 1a — масштабирование интерфейса

## 10.1. Исследуемый аспект

Проверяется влияние увеличения количества компонентов на число HTTP-запросов, если нескольким компонентам одновременно необходим один и тот же server-state.

Этот эксперимент отделяет исследуемое различие от эффекта `React.StrictMode`.

---

## 10.2. Условие

`React.StrictMode` отключён.

Это позволяет исключить повторное выполнение эффектов development-режима и проверить непосредственно связь:

**количество компонентов → количество запросов.**

---

## 10.3. Сценарий

На странице одновременно монтируются **10 независимых компонентов**.

Каждому компоненту необходим один и тот же ресурс:

`/todos`

После загрузки страницы фиксируется количество HTTP-запросов.

---

## 10.4. Manual — useEffect + useState

Каждый из десяти компонентов:

1. имеет собственный `useEffect`;
2. самостоятельно вызывает `fetch`;
3. получает данные `/todos`;
4. сохраняет их в собственном `useState`.

Компоненты не используют общий механизм server-state.

### Результат

**10 компонентов → 10 HTTP-запросов.**

---

## 10.5. React Query

Каждый из десяти компонентов использует `useQuery` для получения того же ресурса.

Для всех компонентов используется одинаковый `queryKey`.

React Query распознаёт обращения как запросы одного server-state и предоставляет компонентам результат через общий механизм query/cache.

### Результат

**10 компонентов → 1 HTTP-запрос.**

---

## 10.6. Результаты

| Подход      | Компоненты | HTTP-запросы |
| ----------- | ---------: | -----------: |
| Manual      |         10 |           10 |
| React Query |         10 |            1 |

---

## 10.7. Наблюдения

Manual демонстрирует прямую зависимость между количеством независимо загружающих данные компонентов и количеством HTTP-запросов.

В исследованной реализации каждый новый компонент создаёт ещё одно независимое обращение к тому же endpoint.

React Query выполняет один сетевой запрос, несмотря на наличие десяти потребителей одного server-state.

Таким образом, различие возникает не из-за `StrictMode`, а из-за способа организации получения одинаковых серверных данных несколькими компонентами.

---

## 10.8. Визуальная фиксация

В магистерской работе:

**Рис. 3.** Manual — 10 запросов к `/todos`.

**Рис. 4.** React Query — один запрос при одновременном использовании данных десятью компонентами.

---

## 10.9. Вывод по эксперименту 1a

Эксперимент показывает, что при независимом использовании `useEffect` / `useState` количество запросов в данной реализации растёт вместе с количеством компонентов.

React Query с одинаковым `queryKey` предотвращает выполнение независимого запроса каждым компонентом и позволяет нескольким компонентам использовать результат одного query.

Следовательно, различие между подходами становится особенно заметным при масштабировании интерфейса.

Важно, однако, что эксперимент сравнивает React Query с базовой ручной реализацией. Ручной подход также может быть расширен собственным общим состоянием или механизмом кэширования, однако такая координация требует дополнительной реализации со стороны разработчика и выходит за границы базового сценария PB1.

# 11. Эксперимент 1b — навигация и возврат к представлению

## 11.1. Исследуемый аспект

Проверяется поведение server-state после ухода пользователя со страницы и последующего возвращения.

Основной вопрос:

**обязательно ли повторное монтирование представления приводит к повторному HTTP-запросу?**

Дополнительно проверяется влияние механизмов React Query, определяющих актуальность и время хранения данных.

---

## 11.2. Сценарий

В приложении существуют два представления:

- `/todos` — использует server-state;
- `/about` — не загружает `/todos`.

Пользователь выполняет:

1. `/todos`;
2. `/about`;
3. повторный переход на `/todos`.

Навигация выполняется внутри SPA без полной перезагрузки приложения.

Фиксируется суммарное количество HTTP-запросов к `/todos` за полный цикл.

---

## 11.3. Manual — useEffect + useState

При первом открытии `/todos` компонент монтируется и выполняет запрос.

После перехода на `/about` компонент размонтируется, а его локальное состояние перестаёт существовать.

При возвращении на `/todos` компонент создаётся заново, `useEffect` снова запускает `fetch`.

### Результат

- первоначальная загрузка — 1 запрос;
- возврат — 1 запрос.

**Итого: 2 HTTP-запроса.**

---

## 11.4. React Query — конфигурация по умолчанию

Проверяется поведение при стандартном:

`staleTime = 0`

После первого получения данные существуют в кэше, однако сразу считаются stale.

При возвращении к представлению активный query может повторно получить данные.

### Результат

**2 HTTP-запроса.**

В этом варианте количественное сетевое поведение совпадает с ручной реализацией.

Это важный результат: само использование React Query не означает автоматического сокращения количества запросов во всех сценариях.

---

## 11.5. React Query — staleTime = 30 s

Следующий вариант:

`staleTime = 30 s`

Пользователь возвращается на `/todos` до истечения 30 секунд.

Данные остаются fresh и могут быть использованы из кэша без повторного HTTP-запроса.

### Результат

**1 HTTP-запрос за весь цикл.**

---

## 11.6. React Query — staleTime = 30 s, gcTime = 5 s

Проверяется дополнительное условие:

- `staleTime = 30 s`;
- `gcTime = 5 s`.

После ухода со страницы query становится неактивным.

Если пользователь отсутствует достаточно долго для удаления query из кэша, при возвращении сохранённых данных уже нет и требуется новое получение server-state.

### Результат

**2 HTTP-запроса.**

---

## 11.7. Результаты

| Реализация / конфигурация                   | HTTP-запросы за цикл | Причина                               |
| ------------------------------------------- | -------------------: | ------------------------------------- |
| Manual                                      |                    2 | повторный mount запускает новый fetch |
| React Query, staleTime = 0                  |                    2 | данные считаются stale                |
| React Query, staleTime = 30 s               |                    1 | fresh-данные используются повторно    |
| React Query, staleTime = 30 s, gcTime = 5 s |                    2 | данные удалены из cache до возврата   |

---

## 11.8. Наблюдения

Эксперимент показывает, что различие между подходами нельзя описывать простым правилом:

**Manual = повторный запрос, React Query = отсутствие повторного запроса.**

При стандартной конфигурации React Query количество запросов оказалось таким же, как при ручной реализации.

Различие заключается в наличии формализованной модели управления жизненным циклом server-state.

`staleTime` определяет период, в течение которого данные считаются актуальными.

`gcTime` влияет на время хранения неактивного query в памяти.

Следовательно, выполнение повторного запроса в React Query зависит от явно определяемых условий состояния query и конфигурации библиотеки.

---

## 11.9. Визуальная фиксация

Для эксперимента 1b отдельные скриншоты Chrome DevTools не являются обязательной частью доказательной базы.

Результат фиксируется количественно в таблице для каждого варианта конфигурации.

Скриншоты из экспериментов 1 и 1a демонстрируют используемый способ регистрации запросов в Chrome DevTools, а эксперимент 1b использует ту же методику измерения.

---

## 11.10. Вывод по эксперименту 1b

Ручная реализация связывает повторное получение данных с повторным монтированием компонента. При отсутствии дополнительного кэширования возврат к представлению приводит к новому HTTP-запросу.

React Query отделяет жизненный цикл server-state от жизненного цикла отдельного компонента, однако это не означает безусловного отсутствия повторных запросов.

При `staleTime = 0` повторный запрос выполняется и результат по количеству запросов совпадает с Manual.

При увеличении `staleTime` ранее полученные fresh-данные могут использоваться без нового обращения к серверу.

При удалении неактивных данных из кэша вследствие `gcTime` повторный запрос снова становится необходимым.

Следовательно, React Query предоставляет механизм управления условиями повторного получения данных, а фактическое сетевое поведение зависит от конфигурации.

| 10 компонентов, StrictMode off            |     10 |           1 | Query предотвращает независимые одинаковые запросы           |
| Навигация, default                        |      2 |           2 | использование Query само по себе не уменьшает число запросов |
| Навигация, staleTime = 30 s               |      2 |           1 | fresh cache позволяет избежать повторного запроса            |
| Навигация, staleTime = 30 s, gcTime = 5 s |      2 |           2 | удаление cache снова требует загрузки                        |

# 13. Ответ на исследовательский вопрос

Результаты PB1 показывают, что выбор подхода к управлению server-state влияет как на количество, так и на условия возникновения повторных HTTP-запросов.

В базовой ручной реализации запрос непосредственно связан с жизненным циклом компонента. Это приводит к повторному выполнению загрузки при повторном запуске эффекта, независимом монтировании нескольких компонентов и повторном монтировании представления.

React Query вводит дополнительный уровень управления между компонентом и сетевым запросом: query идентифицируется через `queryKey`, результат может совместно использоваться несколькими потребителями и сохраняться в кэше независимо от конкретного компонента.

При этом PB1 также показывает, что React Query **не гарантирует минимальное количество запросов автоматически**. При стандартном `staleTime = 0` в сценарии навигации число запросов совпало с ручным подходом. Снижение числа повторных запросов зависит от характера сценария и конфигурации механизмов актуальности и хранения данных.

Таким образом, основное различие заключается не только в абсолютном количестве запросов, но и в механизме управления условиями их повторного выполнения.

---

# 14. Связь результатов PB1 с гипотезой работы

PB1 поддерживает часть общей гипотезы о том, что выбор подхода к управлению server-state влияет на количество и предсказуемость HTTP-запросов.

Результаты показывают:

- различие в количестве запросов действительно существует в определённых сценариях;
- наиболее выраженное различие наблюдается при нескольких потребителях одного server-state;
- React Query позволяет формализовать правила повторного получения данных;
- преимущества React Query не являются безусловными и зависят от сценария и конфигурации;
- ручной подход также может быть расширен дополнительными механизмами, однако они требуют отдельной реализации.

Следовательно, PB1 не подтверждает упрощённое утверждение «React Query всегда выполняет меньше запросов». Он подтверждает более точную гипотезу: **выбор модели управления server-state изменяет сетевое поведение приложения и способы контроля повторных запросов.**

---

# 15. Границы PB1

PB1 намеренно ограничен вопросом получения данных и повторных запросов.

В PB1 **не исследуются**:

- race conditions;
- обработка ошибок и retry;
- background refetch как самостоятельная проблема;
- долгосрочная актуальность данных;
- мутации;
- синхронизация после POST/DELETE;
- параметризованные query;
- координация сложных представлений одного server-state;
- производительность backend;
- время ответа сервера как отдельная метрика.

Эти аспекты рассматриваются в последующих PB.

Такое разделение необходимо, чтобы каждый исследовательский вопрос проверял самостоятельный аспект управления server-state и не дублировал другие эксперименты.

# 16. Ограничения исследования

### Development-режим

Результат первого эксперимента с двумя запросами Manual связан с `React.StrictMode` и не должен интерпретироваться как универсальное поведение production-приложения.

Поэтому эксперимент 1a проводится с отключённым `StrictMode`.

### Базовая ручная реализация

Manual в PB1 представляет базовый подход на основе `useEffect` и `useState`.

Теоретически ручная реализация может быть дополнена:

- общим Context;
- custom hook;
- собственным cache;
- дедупликацией;
- TTL;
- другими механизмами координации.

Следовательно, вывод PB1 относится не к невозможности реализации аналогичного поведения вручную, а к различию между базовым ручным управлением и готовыми механизмами React Query.

### Источник данных

JSONPlaceholder используется как контролируемый внешний источник данных. PB1 не оценивает производительность самого API.

### Метрика

Количество HTTP-запросов является основной метрикой PB1. Время ответа, объём переданных данных, CPU, память и реальная стоимость серверной инфраструктуры отдельно не измеряются.

---

# 17. Почему отдельный эксперимент 1c не выполняется

Первоначально рассматривался дополнительный эксперимент 1c, связанный с повторным открытием представления или дополнительным изменением конфигурации React Query.

После выполнения эксперимента 1b отдельный 1c был исключён.

Причина состоит в том, что 1b уже экспериментально проверяет:

- размонтирование представления;
- повторное монтирование;
- повторное получение данных;
- использование существующего cache;
- влияние `staleTime`;
- влияние `gcTime`.

Дополнительный эксперимент с ещё одним вариантом remount или конфигурации повторял бы уже исследованный механизм и не вводил самостоятельного аспекта исследовательского вопроса.

Поэтому финальная структура PB1 включает **три эксперимента: 1, 1a и 1b**.

---

# 18. Итог PB1

PB1 показывает последовательное развитие проблемы повторных запросов:

**один компонент → множество компонентов → уход и возврат пользователя.**

В базовом ручном подходе получение server-state непосредственно связано с компонентами и их жизненным циклом. Поэтому повторное выполнение эффекта, появление нескольких независимых потребителей или повторное монтирование приводят к новым обращениям к серверу, если разработчик самостоятельно не вводит механизм совместного использования или кэширования.

React Query управляет данными как отдельным server-state, идентифицируемым через `queryKey`, что позволяет дедуплицировать запросы, совместно использовать результаты и определять условия повторной загрузки через настройки актуальности и хранения данных.

При этом эксперимент 1b демонстрирует существенное ограничение упрощённого вывода: React Query не всегда уменьшает количество запросов. При стандартной конфигурации сетевое поведение может совпадать с ручной реализацией.

Таким образом, PB1 подтверждает, что выбор подхода к управлению server-state влияет на количество и предсказуемость повторных HTTP-запросов, однако характер этого влияния зависит от конкретного пользовательского сценария и конфигурации механизма управления данными.

**PB1 считается завершённым.**
