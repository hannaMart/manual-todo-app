# PB4 — Мутации и синхронизация данных (manual)

## 4a — Добавление элемента (add)

### Цель

Исследовать поведение приложения после добавления нового элемента и сравнить две ручные стратегии синхронизации интерфейса с server-state.

### Сценарий

Пользователь добавляет новый элемент в список.

Сравниваются два варианта:

1. после мутации выполняется повторное получение данных (`refetch`);
2. локальное состояние обновляется без повторного получения списка (`setState`).

### Метрики

- количество обращений к API;
- корректность данных в UI;
- способ синхронизации;
- предсказуемость поведения;
- сложность реализации.

### Наблюдения

#### Вариант: refetch

Последовательность:

`ADD → GET`

Выполняются два обращения к API:

- добавление элемента;
- повторное получение списка.

После успешного повторного получения данных интерфейс отображает актуальное серверное состояние.

Преимущества:

- данные повторно считываются из серверного источника;
- клиенту не требуется самостоятельно воспроизводить изменение списка;
- логика синхронизации относительно проста.

Недостатки:

- требуется дополнительное обращение к API;
- увеличивается объём сетевых операций в случае использования реального HTTP API.

#### Вариант: setState

Последовательность:

`ADD → локальное обновление state`

Выполняется одно обращение к API — добавление элемента.

После успешной мутации UI обновляется локально без повторного получения всего списка.

Преимущества:

- отсутствует дополнительный `GET`;
- уменьшается количество обращений к API;
- интерфейс может быть обновлён сразу после успешной мутации.

Недостатки:

- клиентская логика должна корректно обновить локальное состояние;
- возрастает ответственность разработчика за согласованность UI с server-state;
- ошибка в логике локального обновления может привести к рассинхронизации.

### Вывод

Обе стратегии позволяют корректно синхронизировать интерфейс после добавления элемента.

`refetch` повторно получает актуальное серверное представление данных, но требует дополнительного обращения к API.

`setState` позволяет избежать повторного получения списка, однако требует ручного воспроизведения изменения server-state в локальном состоянии.

## 4b — Удаление элемента (delete)

### Цель

Исследовать поведение приложения после удаления элемента и сравнить две ручные стратегии синхронизации интерфейса с server-state.

### Сценарий

Пользователь удаляет элемент из списка.

Сравниваются два варианта:

1. после мутации выполняется повторное получение данных (`refetch`);
2. локальное состояние обновляется вручную (`setState`).

### Метрики

- количество обращений к API;
- корректность данных в UI;
- способ синхронизации;
- предсказуемость поведения;
- сложность реализации.

### Наблюдения

#### Вариант: refetch

Последовательность:

`DELETE → GET`

Выполняются два обращения к API:

- удаление элемента;
- повторное получение списка.

После успешного повторного получения данных удалённый элемент отсутствует в интерфейсе, а UI отражает текущее серверное состояние.

Преимущества:

- список повторно формируется на основе серверных данных;
- не требуется вручную изменять локальную копию списка;
- снижается зависимость результата от логики локального обновления.

Недостатки:

- выполняется дополнительное обращение к API;
- увеличивается количество сетевых операций при использовании реального HTTP API.

#### Вариант: setState

Последовательность:

`DELETE → локальное обновление state`

Выполняется одно обращение к API — удаление элемента.

После успешной мутации элемент вручную удаляется из локального состояния.

Преимущества:

- не требуется дополнительный `GET`;
- уменьшается количество обращений к API;
- интерфейс может быть обновлён непосредственно после успешной мутации.

Недостатки:

- разработчик самостоятельно отвечает за корректное изменение локального состояния;
- ошибка в логике обновления может привести к отображению устаревших данных.

### Вывод

Как и при добавлении элемента, обе стратегии позволяют синхронизировать UI после мутации.

`refetch` повторно получает текущее состояние сервера, тогда как `setState` воспроизводит результат мутации на стороне клиента.

Выбор между ними представляет компромисс между количеством обращений к API и объёмом ручной логики синхронизации.

## 4c — Сравнение стратегий синхронизации после мутации

### Цель

Сравнить стратегии синхронизации, исследованные в сценариях 4a и 4b.

4c не является отдельным интерактивным экспериментом. Он представляет аналитический итог результатов добавления и удаления элементов.

### Сравнение

| Стратегия  |        Обращения к API после мутации | Источник обновления UI               | Ответственность клиента |
| ---------- | -----------------------------------: | ------------------------------------ | ----------------------- |
| `refetch`  |      дополнительное получение данных | повторно полученные серверные данные | ниже                    |
| `setState` | без дополнительного получения списка | локальное состояние                  | выше                    |

### Наблюдения

При ручном управлении server-state синхронизация после мутации должна быть явно реализована разработчиком.

Возможны разные стратегии:

- повторное получение данных;
- ручное изменение локального состояния.

Повторное получение данных уменьшает количество логики, необходимой для воспроизведения изменения на клиенте, но требует дополнительного обращения к API.

Локальное обновление состояния позволяет уменьшить количество обращений к API, однако переносит большую часть ответственности за согласованность данных на клиентскую реализацию.

---

# Итог PB4 — manual

Ручное управление server-state не определяет единой стратегии синхронизации после мутации.

Разработчик самостоятельно решает:

- выполнять ли повторное получение данных;
- изменять ли локальное состояние;
- каким образом поддерживать согласованность UI с серверными данными.

Подход через `setState` позволяет сократить количество обращений к API, но требует дополнительной ручной логики.

Подход через `refetch` требует дополнительного обращения к API, зато использует повторно полученное серверное состояние как источник данных для интерфейса.

Таким образом, ключевым различием между стратегиями является компромисс между количеством обращений к API и объёмом ответственности клиентского кода за синхронизацию данных.
