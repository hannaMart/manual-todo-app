# PB6a — Shared: совместное использование server-state

## 1. Исследовательский вопрос

Как выбранный способ управления server-state влияет на совместное использование одних и тех же серверных данных несколькими компонентами React-приложения?

В PB6a исследуется организация совместного доступа к server-state при одновременном использовании одного серверного ресурса двумя компонентами.

Сравниваются три реализации:

- Manual — Props;
- Manual — Context API;
- React Query — общий queryKey и cache.

Эксперимент направлен на выявление различий в организации общего состояния, количестве API-запросов и способах предоставления серверных данных нескольким компонентам.

## 2. Цель эксперимента

Проверить, каким образом два компонента React-приложения могут использовать один набор серверных данных без необходимости выполнять отдельный API-запрос для каждого компонента.

Установить:

1. Сколько API-запросов выполняется при одновременном монтировании двух компонентов.
2. Получают ли оба компонента одинаковые серверные данные.
3. Где организовано общее состояние.
4. Каким образом компоненты получают доступ к общим данным.
5. Какие механизмы необходимо реализовать самостоятельно при ручном управлении server-state и какие предоставляет React Query.

## 3. Условия эксперимента

Во всех трёх реализациях используются одинаковые исходные данные и одна серверная операция.

Источник данных: коллекция TODOS из fakeServer/db.js.

Исходное состояние:

| ID  | Title                   | Completed |
| --- | ----------------------- | --------- |
| 1   | Drink 2 litres of water | false     |
| 2   | Task 2                  | true      |
| 3   | Task 3                  | false     |
| 4   | Task 4                  | true      |

Для получения данных используется функция fakeFetchPb6Todos() из fakeServer/fakeAPI.js.

Характеристики функции:

- имитация асинхронного API-запроса;
- задержка ответа — 800 мс;
- возврат массива из четырёх задач;
- регистрация начала и завершения каждого вызова в консоли;
- отдельный счётчик запросов PB6.

Во всех вариантах два компонента одновременно отображают одинаковый список задач.

Оба компонента используют одинаковую структуру отображения данных.

Серверные данные не изменяются.

Разные представления данных и мутации в PB6a не исследуются.

Количество обращений определяется по логам fakeAPI. Поскольку используется имитация API, фиксируются API-запросы, а не реальные HTTP-запросы.

## 4. Реализация Manual — Props

Файл:

manual-todo-app/src/experiments/exp6-koordynacja/shared/shared-props.jsx

### 4.1. Организация состояния

Родительский компонент SharedProps выполняет загрузку серверных данных с помощью useEffect.

Полученный массив сохраняется в локальном состоянии родителя с помощью useState.

Родитель также управляет состояниями загрузки и ошибки.

После успешного завершения запроса данные передаются двум дочерним компонентам через props.

Схема:

fakeAPI → SharedProps (useState) → props → Component A / Component B

Оба дочерних компонента являются отдельными экземплярами TodoList.

Каждый получает один и тот же массив todos:

```jsx
<TodoList title="Component A" todos={todos} />
<TodoList title="Component B" todos={todos} />
```

Дочерние компоненты не выполняют собственных API-запросов и не создают независимых состояний для хранения полученного массива.

### 4.2. Результат проверки

При открытии страницы зафиксирован один API-запрос:

```text
[PB6][GET] #1 START
[PB6][GET] #1 END
```

После завершения загрузки оба компонента отображают одинаковый список из четырёх задач.

Дополнительные API-запросы для дочерних компонентов отсутствуют.

### 4.3. Вывод

Ручное управление server-state с помощью useState, useEffect и props позволяет организовать совместное использование серверных данных двумя компонентами без дублирования запросов.

Для этого разработчик размещает загрузку и хранение состояния в общем родительском компоненте и явно передаёт данные заинтересованным дочерним компонентам.

В проверенном сценарии один API-запрос обеспечивает получение данных обоими компонентами.

## 5. Реализация Manual — Context API

Файл:

manual-todo-app/src/experiments/exp6-koordynacja/shared/shared-context.jsx

### 5.1. Организация состояния

В данной реализации используется TodosContext и компонент TodosProvider.

TodosProvider выполняет загрузку серверных данных с помощью useEffect и сохраняет полученный массив в useState.

Данные, состояние загрузки и ошибка предоставляются дочерним компонентам через Context API.

Схема:

fakeAPI → TodosProvider (useState) → Context API → Component A / Component B

Оба дочерних компонента получают доступ к общему состоянию с помощью useContext:

```jsx
const { todos, loading, error } = useContext(TodosContext);
```

Передача массива todos через props не требуется.

Загрузка данных выполняется централизованно внутри TodosProvider.

Дочерние компоненты не выполняют собственных API-запросов и не хранят независимые копии серверных данных.

### 5.2. Результат проверки

При открытии страницы зафиксирован один API-запрос.

Оба компонента отображают одинаковый список из четырёх задач.

Дополнительные запросы со стороны дочерних компонентов отсутствуют.

### 5.3. Вывод

Context API позволяет организовать совместное использование server-state без явной передачи серверных данных через props.

Однако Context API самостоятельно не выполняет загрузку, кэширование или синхронизацию серверных данных.

В исследованной реализации загрузка и хранение состояния по-прежнему организуются разработчиком с помощью useEffect и useState внутри TodosProvider.

Таким образом, Context API изменяет механизм предоставления общего состояния компонентам, но не заменяет ручную реализацию логики получения серверных данных.

## 6. Реализация React Query

Файл:

query-todo-app/src/experiments/exp6-koordynacja/shared.jsx

### 6.1. Организация состояния

В реализации React Query оба дочерних компонента самостоятельно используют хук useQuery.

Для обращения к одному серверному ресурсу применяется одинаковый queryKey:

```jsx
useQuery({
  queryKey: ["pb6-todos"],
  queryFn: fakeFetchPb6Todos,
  staleTime: 60_000,
  refetchOnMount: false,
  refetchOnWindowFocus: false,
});
```

Оба компонента работают с одним QueryClient.

React Query использует queryKey для идентификации серверных данных в общем кэше.

При одновременном обращении компонентов к одному ресурсу библиотека совместно использует выполняющийся запрос и его результат.

Схема:

Component A → useQuery → общий QueryClient / cache

Component B → useQuery → общий QueryClient / cache

Оба компонента обращаются к одной записи кэша, идентифицируемой queryKey ["pb6-todos"].

Родительский компонент не хранит полученный массив в собственном useState и не передаёт серверные данные через props.

Дополнительный пользовательский Context для передачи массива задач не создаётся.

### 6.2. Настройки эксперимента

Для данного сценария установлены:

- staleTime: 60 000 мс;
- refetchOnMount: false;
- refetchOnWindowFocus: false.

Настройки фиксируют условия повторного получения данных и ограничивают дополнительные запросы, не относящиеся непосредственно к проверке совместного доступа.

Количество API-запросов проверяется при определённом исходном состоянии QueryClient, поскольку ранее заполненный кэш может повлиять на результат.

### 6.3. Результат проверки

При открытии страницы зафиксирован один API-запрос:

```text
[PB6][GET] #1 START
[PB6][GET] #1 END
```

После завершения загрузки оба компонента отображают одинаковый список из четырёх задач.

Несмотря на то что каждый компонент самостоятельно вызывает useQuery, дополнительный API-запрос для второго компонента не выполняется.

Оба компонента используют общий результат запроса, связанный с одинаковым queryKey.

### 6.4. Вывод

React Query обеспечивает совместное использование server-state посредством общего кэша и идентификации данных через queryKey.

Каждый компонент может самостоятельно обращаться к серверным данным через useQuery без необходимости организовывать их передачу через родительский компонент или пользовательский Context.

В проверенном сценарии два компонента получили одинаковые данные после выполнения одного API-запроса.

При этом по количеству запросов React Query не показал отличий от двух ручных реализаций.

## 7. Сравнение трёх реализаций

| Критерий                                                | Manual — Props     | Manual — Context API | React Query         |
| ------------------------------------------------------- | ------------------ | -------------------- | ------------------- |
| Источник серверных данных                               | fakeAPI            | fakeAPI              | fakeAPI             |
| Компонентов-потребителей                                | 2                  | 2                    | 2                   |
| API-запросов                                            | 1                  | 1                    | 1                   |
| Хранение общего состояния                               | useState родителя  | useState провайдера  | QueryClient / cache |
| Получение данных компонентами                           | props              | useContext           | useQuery            |
| Организация загрузки                                    | useEffect родителя | useEffect провайдера | useQuery и queryFn  |
| Ручная передача массива через props                     | Да                 | Нет                  | Нет                 |
| Пользовательский Provider для массива                   | Нет                | Да                   | Нет                 |
| Самостоятельное хранение массива в дочерних компонентах | Нет                | Нет                  | Нет                 |

Все три реализации проверены экспериментально.

В каждом варианте зафиксирован один API-запрос и одинаковое отображение серверных данных двумя компонентами.

## 8. Общие выводы

### 8.1. Количество API-запросов

Все три реализации обеспечили совместное использование серверных данных двумя компонентами после выполнения одного API-запроса.

Это показывает, что дублирование запросов не является обязательной характеристикой ручного управления server-state.

Разработчик может самостоятельно организовать общий источник состояния и обеспечить его совместное использование несколькими компонентами.

В проверенном сценарии React Query не обеспечил сокращения количества API-запросов относительно оптимизированных ручных реализаций.

### 8.2. Организация общего состояния

В Manual — Props общее состояние размещается в родительском компоненте.

В Manual — Context API общее состояние размещается в Provider и предоставляется компонентам через Context API.

В React Query общее состояние организуется с использованием QueryClient и кэша, а компоненты обращаются к нему через useQuery с одинаковым queryKey.

Таким образом, различие между исследуемыми подходами заключается прежде всего в способе организации общего состояния и доступа к нему, а не в содержимом отображаемых данных.

### 8.3. Роль Context API

Context API позволяет устранить необходимость явной передачи массива серверных данных через props.

При этом загрузка данных, обработка ошибок и хранение server-state остаются частью ручной реализации.

Следовательно, Context API рассматривается как механизм организации совместного доступа к состоянию, а не как самостоятельная замена специализированной библиотеки управления server-state.

### 8.4. Роль React Query

React Query предоставляет общий кэш, идентификацию серверных данных через queryKey и механизм совместного использования результатов запросов.

Разработчику не требуется самостоятельно создавать общий useState и отдельную систему передачи полученного массива компонентам.

Однако данный сценарий не устанавливает преимуществ React Query по количеству запросов, поскольку ручные реализации также обеспечивают совместный доступ без их дублирования.

### 8.5. Ограничения эксперимента

PB6a рассматривает простой сценарий с двумя компонентами, одновременно использующими одинаковые неизменяемые серверные данные.

Эксперимент не исследует:

- сложные деревья компонентов;
- различия производных представлений;
- изменение серверных данных;
- распространение изменений между компонентами;
- дополнительные запросы при повторном монтировании;
- производительность рендеринга;
- сравнительную трудоёмкость реализации в крупных приложениях.

Поэтому результаты PB6a не позволяют сделать общий вывод о превосходстве одного подхода над другим.

Эксперимент устанавливает фактические различия в механизмах организации совместного доступа к server-state.

## 9. Переход к PB6b

Следующая часть исследования — PB6b (representations).

В отличие от PB6a, где два компонента отображают одинаковый список задач, в PB6b три компонента будут использовать один набор серверных данных для формирования разных представлений:

- Component A — полный список задач;
- Component B — общее количество задач;
- Component C — количество выполненных и невыполненных задач.

Цель PB6b — проверить организацию разных представлений одного server-state без создания дополнительных независимых источников серверных данных.

Мутации и распространение изменений между компонентами будут исследованы отдельно в PB6c.
